# Contributing to commUNITY

First of all, thank you for your interest in contributing to **commUNITY**.

commUNITY is intended to be built as an open-source, community-driven project. Contributions are not limited to writing code. Ideas, documentation, architecture, community research, governance and real-world feedback are equally valuable.

> **Build the infrastructure. Empower the community. Let the community govern it.**

---

## 🌱 Ways to Contribute

There are many ways to contribute to commUNITY.

### 💡 Ideas

Have an idea for improving the platform?

You can:

* Open a GitHub Issue
* Participate in an existing discussion
* Propose a new feature
* Suggest improvements to an existing capability

For significant changes, consider creating a **Unity Improvement Proposal (UIP)**.

# 🗳️ Unity Improvement Proposals

Significant changes to commUNITY should be discussed transparently through **Unity Improvement Proposals (UIP)**.

Examples include:

```text
UIP-0002
Community Identity & Onboarding

UIP-0003
Community Contribution Credit Framework

UIP-0004
Treasury & Blockchain Architecture

UIP-0005
Governance Framework
```

A typical proposal lifecycle is:

```text
Draft
  ↓
Discussion
  ↓
Proposed
  ↓
Voting
  ↓
Accepted / Rejected
  ↓
Implementation
```

Not every code change requires a UIP.

Use a UIP when a change could materially affect the project's:

* Vision
* Governance
* Community rules
* Identity model
* Contribution model
* Financial transparency
* Core architecture
* Long-term direction

# 🐛 Reporting Issues

Before opening an issue:

1. Search existing issues.
2. Check whether the issue has already been reported.
3. Provide enough information for someone else to reproduce the problem.

A useful issue should include:

* Clear description
* Expected behavior
* Actual behavior
* Steps to reproduce
* Relevant logs or screenshots
* Environment information
* Version or commit, where applicable

Please avoid including sensitive personal information in issues.

---

# 🔀 Pull Requests

Pull requests are welcome.

Before submitting a PR:

* Keep the change focused.
* Explain what the PR changes.
* Explain why the change is needed.
* Add or update tests where appropriate.
* Update documentation where necessary.
* Make sure existing tests continue to pass.
* Avoid unrelated changes in the same PR.

A PR should generally solve **one problem or introduce one coherent change**.

---

# 📝 Commit Guidelines

There is no rigid commit format at this stage.

However, commits should be:

* Clear
* Concise
* Descriptive
* Focused on a logical change

Prefer:

```text
Add resident verification workflow
```

over:

```text
changes
```

---

# 🔍 Code Review

Code review is intended to improve the project, not to judge contributors.

Reviewers should focus on:

* Correctness
* Security
* Maintainability
* Performance
* Simplicity
* Testability
* User impact
* Alignment with project principles

Contributors are encouraged to explain design decisions and openly discuss alternatives.

---

# 🔐 Security

Please do **not** report security vulnerabilities through public GitHub issues.

Security vulnerabilities should be reported privately through the security contact/process defined by the repository maintainers.

Do not include:

* Personal information
* Authentication credentials
* Private keys
* Identity documents
* Community member information
* Sensitive financial information

in public issues or pull requests.

---

# 🔒 Privacy

commUNITY deals with concepts such as community identity, residents, workers and community financial information.

Contributors must take privacy seriously.

Do not commit:

* Aadhaar information
* Personal identification documents
* Phone numbers or addresses
* Private financial information
* Authentication secrets
* API keys
* Private community records
* Real resident datasets

Use synthetic or anonymized data for development and testing.

---

# 🧭 Design Principles

Contributions should align with the core principles of commUNITY:

### Community First

Technology should serve the community.

### Verified Participation

Community membership should be trusted.

### Privacy by Default

Sensitive information should remain protected.

### Transparency

Important community activities should have an auditable history.

### Contribution Matters

Meaningful community contribution should be recognized.

### Blockchain Where It Matters

Blockchain should be used where it provides meaningful value.

### No Pay-to-Govern

Financial contribution should not automatically translate into governance power.

### Community-Owned Data

Communities should retain control over their data.

# 🤝 Respectful Collaboration

Different contributors will have different:

* Technical backgrounds
* Community experiences
* Opinions
* Priorities
* Approaches

Healthy disagreement is expected.

We encourage contributors to:

* Ask questions
* Explain reasoning
* Challenge assumptions
* Provide evidence
* Listen to alternative perspectives
* Change their position when new information emerges

Technical disagreement is welcome.

Personal attacks are not.

See [`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md).

# 🚀 Getting Started

If you are new to the project, a good starting point is:

1. Read [`README.md`](README.md).
2. Read [`docs/vision.md`](docs/vision.md).
3. Read [`proposals/UIP-0001-founding-proposal.md`](proposals/UIP-0001-founding-proposal.md).
4. Explore open issues and discussions.
5. Look for issues marked as suitable for new contributors.
6. Start a discussion if you have an idea that does not yet have an issue.

---

# 🌍 Community Before Code

commUNITY is ultimately a community project.

The most valuable contribution may not always be a line of code.

It could be:

* A better idea
* A better process
* A real-world community problem
* A useful government procedure
* A governance improvement
* A security concern
* A better user experience
* A lesson learned from operating a community

If it helps make commUNITY more useful, trustworthy or accessible to communities, it is a valuable contribution.
